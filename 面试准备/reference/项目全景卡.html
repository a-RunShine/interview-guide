四条分层铁律（来自 AGENTS.md，被追问“你们代码规范”时直接背这四条）：

  1. Controller 只做路由、校验、委托；编排在 Service；@Transactional 只在 Service 且范围最小。
  2. 基础设施能力必须落在 common/ 或 infrastructure/，不散落到业务 Service。
  3. 对外统一返回 Result<T>，禁止直接返回 Entity。
  4. LLM / S3 / 外部 HTTP 调用不得放在数据库事务内。（第 4 条最常被追问）

G六个关键设计决策（一句话版 · 详细话术见第 5 课）

决策理由替代方案与代价
PG + pgvector 单库，不引独立向量库关系数据与向量同一事务语义演进；单实例够用；精简组件Milvus / Qdrant / ES：检索更强，多一个运维组件
Redis Stream 而非 Kafka 做异步Redis 已在架构里（缓存+限流+会话），复用不加组件；AbstractStreamProducer/Consumer 统一了生产消费与 ACKKafka / RabbitMQ：吞吐生态更强，加运维成本
LLM 接入收敛到 LlmProviderRegistry + StructuredOutputInvoker运行期可切默认模型不改代码；重试与降级集中一处，业务只声明“要什么结构”各模块直连 SDK：实现简单，但换模型要改代码、重试逻辑重复
文字/语音共用 UnifiedEvaluationService两种形态评估口径必须可比（同报告结构、同评分维度）各写一套：可特化，但结果不可比、维护双份
出题策略外置为 resources/skills/<方向>/SKILL.md内置 10+ 方向，运行期由 Spring AI Agent Utils 加载；新增方向只加目录，不改 Java硬编码在 Java：改方向要动代码、发版
运行期 Provider 配置落用户目录写 ~/.interview-guide/，不污染源码/jar；API Key 加密落盘（密钥来自 APP_AI_CONFIG_ENCRYPTION_KEY）写回 application.yml：容器内不可写、易误提交密钥

H两条最常被要求“走一遍”的数据流

① 简历上传 → 异步分析 → PDF（最典型，四层全串）

ResumeController → ResumeUploadService
   ├─ 校验类型/大小 → 计算内容哈希 → 按 hash 查重（命中复用）
   ├─ 写 S3（RustFS） → 落库 ResumeEntity(PENDING)
   ├─ Producer 投递 → Redis Stream（XADD） → 立即返回 Result(PENDING)
   └─ 前端轮询 GET /api/resumes
AnalyzeStreamConsumer
   ├─ Tika 解析 + 文本清洗
   ├─ StructuredOutputInvoker 结构化输出（LLM）
   └─ 更新 ResumeAnalysisEntity（COMPLETED / FAILED，最多重试 3 次）
导出：GET /api/resumes/{id}/export → iText PDF

② RAG 问答（查询改写 → 向量检索 → SSE 流式）

POST /api/knowledgebase/query (SSE)
   → KnowledgeBaseQueryService
   → LLM 查询改写（prompts/knowledgebase-query-rewrite.st）
   → pgvector 相似度检索（TopK + 阈值 · COSINE）
   → 组装上下文（knowledgebase-query-system/user.st）
   → LLM 流式 token → SSE 逐块推送 → 前端虚拟列表打字机渲染
   → 持久化 RagChatMessageEntity
