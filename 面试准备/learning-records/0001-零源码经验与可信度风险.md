# 起点基线：零源码经验 + 一个必须处理的可信度风险

## 已有基础（已核实，非自称）

- 仓库是 `Snailclimb/interview-guide` 的**纯净上游克隆**（HEAD `b2d1ca0`，无 fork、无自有提交）。
- `find . -newer .git/index` 显示除 `app/bin/**/*.class` 与 `.arch-docs`、`.workbuddy` 外，
  **无任何源码改动** → 用户"只跑起来过，没改过"的自述属实，且大概率跑过测试（有测试类 .class 产物）。
- 用户自评"几乎没读过代码"。因此**不能在课程里预设任何 Spring / Spring AI / pgvector 的先验知识**，
  术语首次出现必须解释。

## 关键发现：框架与事实之间有一处矛盾（决定了课程顺序）

用户在提问中选择了「如实说明是开源项目 + 我的二次开发」作为面试讲法，
但同时确认**自己从未改过这个项目**。两者直接冲突：照此说法讲，只是把"我做的项目"换成
"我改过的项目"，**谎言换了包装**，追问"你具体改了什么"时同样会崩。

**Implications（本课之后所有设计都受此约束）：**

1. 课程**不能**从架构讲解开始。第一优先级是**制造真实改动**，把话术的地基夯实。
   顺序：攒弹药 → 建骨架 → 练表达。
2. 用户当前真正稀缺的不是知识，是**可讲的第一手经历**。所有课程都要产出可落到面试回答的具体素材。
3. 判分标准（Success looks like）必须以"能扛住追问"锚定，而不是"能背出多少"。
   用户没有撒谎的动机，只是选了看起来最优的选项而没意识到与事实冲突 ——
   这是**认知盲区**，不是诚信问题，教学上处理方式是补事实而非讲道理。
