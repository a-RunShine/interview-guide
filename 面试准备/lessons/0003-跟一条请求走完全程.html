InterviewGuide 面试准备 / 阶段 1 · 理解骨架 / 第 3 课

跟一条真实请求走完全程

「简历上传 → Redis Stream 异步分析 → PDF」。这一条链路一次串起四层，是读懂这个项目最短的路。

按你的要求，从这一课起只做理解，不动任何代码。贡献的事挂起，等你哪天觉得「这里我知道该怎么改」再说。

先说为什么挑这条链路，而不是从 common/ 开始读：

这条链路的特殊性

  • 它是唯一一条把四层都走完的链路：Controller → Service → infrastructure（文件/解析）→ common（异步模板 + LLM）→ Redis Stream 消费者。
  • 它是最简单的业务模块（约 1.8K 行 / 16 文件）。其他模块都是它的加强版——读懂它，再看知识库、面试、语音，结构都是同一个模子。
  • 面试官问「你讲讲一个请求在你们系统里怎么走」，答得好坏几乎全取决于能不能把这条链路说顺。
  • 后面每一课的内容都从这里长出来：第 7 课（Stream 模板细节）、第 8 课（LLM 接入）、八股课（事务边界、线程池）都能挂在这条链路上。

2同步段：上传接口做的 8 件事

读 ResumeUploadService.uploadAndAnalyze(MultipartFile)（共 235 行，主方法在第 48–111 行）。它按顺序做了 8 件事，每一步都有日志埋点——这不是装饰，是刻意留的可观测性，后面第 10 课会讲。

同步段 · 在 HTTP 请求线程里跑完
  1. validateFile(file, 10MB, "简历") —— 大小与基础校验
  2. detectContentType(file) → 白名单校验，不支持就抛异常
  3. findExistingResume(file) —— SHA-256 内容哈希去重，命中则直接返回历史结果（duplicate: true）
  4. parseResume(file) —— Tika 抽文本；抽不出（如扫描版 PDF）就抛 RESUME_PARSE_FAILED
  5. storageService.uploadResume(file) —— 写 S3，拿到 fileKey / fileUrl
  6. saveResume(...) —— 落库，状态置 PENDING
  7. analyzeStreamProducer.sendAnalyzeTask(id, text) —— 只投递，不执行
  8. 组装 Map 返回 —— 状态是 PENDING

耗时日志把这段拆成「解析耗时 / 存储耗时 / 总耗时」三段——因为这三段是最可能变慢的地方。

第 7 步是同步与异步的分界
异步段 · 在消费者线程里跑，HTTP 请求早已返回
  1. 消费者从 Stream 取到消息
  2. shouldSkip —— 实体不存在、或已是 COMPLETED，就跳过
  3. markProcessing —— 状态置 PROCESSING
  4. processBusiness → gradingService.analyzeResume(content) —— 唯一调 LLM 的地方
  5. saveAnalysis(resume, analysis) —— 结果落库
  6. markCompleted —— 状态置 COMPLETED

前端以固定间隔轮询 GET /api/resumes，看 analyzeStatus 与最新分数。

面试必答：为什么上传不阻塞？

同步段只做不需要大模型的事：校验、解析文本、写对象存储、落库、投递。真正耗时的 LLM 评分被推到消费者里。
一句话版本：「上传接口的职责是把它登记进系统并排好队，不是把它算完。」

3投递段：模板方法模式

AbstractStreamProducer 只有 56 行，结构是教科书级的模板方法：父类写死骨架（sendTask），子类只填 5 个钩子。

// 父类：骨架固定，失败一定走 onSendFailed
protected boolean sendTask(T payload) {
  try {
    String messageId = redisService.streamAdd(streamKey(), buildMessage(payload),
                                               AsyncTaskStreamConstants.STREAM_MAX_LEN);
    log.info("{}任务已发送到Stream: {}, messageId={}", taskDisplayName(), payloadIdentifier(payload), messageId);
    return true;
  } catch (Exception e) {
    log.error("发送{}任务失败: {}, error={}", taskDisplayName(), payloadIdentifier(payload), e.getMessage(), e);
    onSendFailed(payload, "任务入队失败: " + e.getMessage());
    return false;
  }
}

// 子类必须实现的 5 个钩子
protected abstract String taskDisplayName();               // 日志用
protected abstract String streamKey();                     // 发到哪条流
protected abstract Map<String, String> buildMessage(T payload);
protected abstract String payloadIdentifier(T payload);    // 日志用，标识是哪个任务
protected abstract void onSendFailed(T payload, String error);

AnalyzeStreamProducer 填的答案是：流 key 是 resume:analyze:stream，消息体三个字段——resumeId / content / retryCount=0，投递失败时把实体状态置 FAILED。

两个值得单独记住的细节

① STREAM_MAX_LEN = 1000：投递时带上了这个长度上限，Redis 会自动裁剪旧消息。否则 Stream 会无限增长——这是用 Redis 当队列时最常见的坑之一。

② retryCount 写在消息体里，不是靠 Redis 投递次数计。为什么这么设计，见第 5 节，那是本课最重要的判断。

4消费段：一个五出口的状态机

AbstractStreamConsumer.processMessage 是整个异步机制的心脏。它对每条消息有五种结局，其中四种都是「ACK 后丢弃」：

  • 解析失败 → ACK 丢弃
    消息体格式坏了。不能让它一直重投堵住队列（毒丸消息）。
  • payload 为 null → ACK 丢弃
    子类 parsePayload 判定字段缺失（如 resumeId 或 content 为 null）。
  • shouldSkip 返回 true → ACK 丢弃
    这是幂等保护。简历这边：实体不存在，或状态已是 COMPLETED，就不重复烧 LLM 配额。
  • tryMarkProcessing 返回 false → ACK 丢弃
    没抢到任务的领取权。默认实现永远返回 true，只有需要原子领取的消费者才覆写。
  • processBusiness 成功 → markCompleted → ACK
    正常路径。
  • processBusiness 抛异常 → 重试或标记失败 → ACK
    见下一节。注意：失败也会 ACK。

还有三个实现细节值得看，都是「这个项目的代码规范不只是写着好看」的证据：

细节为什么这样写
线程池显式写成 ThreadPoolExecutor(1, 1, ...)，不用 Executors.newSingleThreadExecutor()AGENTS.md 明令禁止 Executors.newXxxThreadPool()——它默认用无界队列，队列积压时可能 OOM。这里显式配置并指定了拒绝策略 AbortPolicy。这是项目规则被真实执行的证据。
消费者名 = 前缀 + UUID 前 8 位每个消费者实例名字唯一，才能支持多实例部署时各自持有自己的 pending 列表。
消费循环带 PENDING_IDLE_TIMEOUT_MS = 5 分钟 与 PENDING_CLAIM_BATCH_SIZE = 10这是 Redis Stream 的 pending 消息认领：某个消费者进程崩了、消息没 ACK，5 分钟后别的消费者可以把它领过来重做。这是 Redis Stream 比 List 强的关键，也是它敢当队列用的原因。

5本课最重要的判断：失败为什么也 ACK

看 processMessage 的异常分支（第 131–141 行）：

} catch (Exception e) {
  log.error("{} task failed: {}", taskDisplayName(), payloadIdentifier(payload), e);
  if (retryCount < AsyncTaskStreamConstants.MAX_RETRY_COUNT) {   // MAX_RETRY_COUNT = 3
    retryMessage(payload, retryCount + 1);                        // 重新 XADD 一条新消息
  } else {
    markFailed(payload, truncateError(...));
  }
  ackMessage(messageId);                                          // 无论如何都 ACK
}

关键在最后一行：不管是重试还是彻底失败，原消息都被 ACK 掉了。重试不是「让 Redis 把这条消息再投一次」，而是 retryMessage 重新 XADD 一条全新的消息，把 retryCount+1 写在新消息体里。

这个设计换来了什么 / 代价是什么

换来：重试次数完全可控（计数在消息体里，不依赖 Redis 的投递计数）；业务失败不会变成无限重投；重试的消息自带完整上下文（content 也重新带上了）。

代价：如果 retryMessage 里的那次 streamAdd 也失败，任务就真的丢了——代码里只能 catch 后把状态置 FAILED，靠状态字段兜底，没有补偿扫描去捞它。

但注意：pending 认领机制仍然开着。所以这个系统里其实有两套重试机制，各管一段：

机制兜住什么情况计数依据
业务重试（retryMessage 重新入队）LLM 调用失败、解析失败等业务层异常消息体里的 retryCount，上限 3
Pending 认领（XAUTOCLAIM 语义）消费者进程崩了，消息既没 ACK 也没处理完Redis 侧的 pending 空闲时长，5 分钟

把这段说清楚，比背「我用了 Redis Stream」高一个量级。面试官问「消息丢了怎么办」，答案就是这两层。

6事务边界：同一个类里为什么两种写法

这是我在读 ResumeUploadService 时觉得最值得单独讲的一处。同一个类里，两个方法用了完全不同的模式：

 uploadAndAnalyzereanalyze
写操作只有「插入一条新记录」「读实体 → 改状态 → 清错误 → 保存」一组写
事务方法上没有手写事务包装显式用 transactionalExecutor.run(...) 包成一个事务
投递位置落库之后事务提交之后（代码注释原文：「事务提交后再发送分析任务到 Stream」）

为什么 reanalyze 必须把投递挪到事务外？推一遍因果：

  1. 如果投递发生在事务内部，消息会在事务提交之前就进 Stream。
  2. 消费者可能立刻抢到这条消息，去读实体——此时读到的还是未提交的旧状态（COMPLETED 或 PROCESSING）。
  3. shouldSkip 看到 COMPLETED，判定「已分析过」，ACK 丢弃。
  4. 结果：用户点了「重新分析」，事务提交了、状态也改回 PENDING 了，但任务永远不会被执行——前端一直转圈。
这条因果链正好命中项目铁律

AGENTS.md 里写着：「LLM、S3、外部 HTTP 调用不得放在数据库事务内」。Redis 投递同理。
面试里被问「事务怎么写」，你把这条讲出来——不是背规则，而是说清违反规则会产生什么错误——分量完全不同。

7模板的扩展点：五个消费者，只有一个用上了

AbstractStreamConsumer 留了个钩子 tryMarkProcessing，默认实现无条件返回 true。全项目有 5 个消费者子类：

子类所在模块是否覆写 tryMarkProcessing
AnalyzeStreamConsumerresume否（用默认）
VectorizeStreamConsumerknowledgebase否（用默认）
QuestionGenStreamConsumerknowledgebase是 —— 走 stateService.tryMarkProcessing(kbId, taskId)
EvaluateStreamConsumerinterview否（用默认）
VoiceEvaluateStreamConsumervoiceinterview否（用默认）

为什么只有题库生成需要覆写？因为它的消息里带 taskId，可以拿它做幂等键——「只有当这个 taskId 对应的任务还没被领取时，才允许置为 PROCESSING」。其余四个没有这么细的幂等粒度，用默认行为就够。

这个对比本身就是一句好答案

被问「你怎么设计可复用的异步组件」，可以答：「骨架写死不变的部分，变化的部分留成钩子；钩子给一个够用的默认实现，只有真正需要特殊语义的场景才覆写。」然后举这 5 个消费者里 1 个覆写的例子——这是有代码支撑的答案，不是泛泛而谈。

8三个可以主动提出的观察

这三条是我读代码时的发现，都不需要改代码，但都能在面试里主动说出来。主动指出问题比等着被问出来强得多——它证明你不只是读过，还想过。

观察一 · 状态回写失败会被吞掉

AnalyzeStreamConsumer.updateAnalyzeStatus 里是 catch (Exception e) { log.error(...) }：只记日志，不抛出。
后果：如果 markCompleted 的数据库写入失败，这个异常被吞掉，但消息已经被 ACK。于是实体状态永远停在 PROCESSING，队列里也没有任何待处理任务，前端会一直转圈，且没有兜底扫描去修正。
我会怎么说：「这类『状态回写失败』我倾向至少上报一个指标，或者加一个定时扫描把超时的 PROCESSING 记录捞回来重投。」

观察二 · 先写对象存储再落库，没有补偿

第 5 步写 S3，第 6 步才落库。如果第 6 步失败，S3 里会留下一个没有数据库记录的孤儿文件，而且没有清理机制。
注意别把答案说简单了：反过来的顺序（先落库再上传）也不对——那会留下「有记录但没文件」的坏数据。更完整的做法是两阶段提交或定时对账。能说出「两种顺序都有问题」，比只指出一个问题更显水平。

观察三 · 重新上传一份「之前分析失败」的简历不会自动重试

handleDuplicateResume 命中哈希后，有历史分析结果就返回它；没有则只返回当前状态，不重新投递任务。
这是「不重复烧 LLM 配额」的保守取舍，但用户视角是「我重新上传了，怎么还是失败」。需要手动调 POST /api/resumes/{id}/reanalyze。这种「设计取舍带来体验代价」的点，面试里很好用。
