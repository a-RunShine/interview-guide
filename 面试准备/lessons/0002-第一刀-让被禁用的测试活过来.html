第一刀：让被禁用的测试活过来

本课的作业不是读代码，是产出一个能在面试里讲 3 分钟的改动。约 1 小时。

你在第 1 课选的框架是「如实说开源 + 我的二次开发」。要让它成立，你需要一个真实的改动。现在有一个比 end_phase 好得多的目标。

1你要交付什么

一句话任务

把 VoiceInterviewServicePauseTest 这个空的 @Disabled 占位类，重写成 6 个真实跑得起来的单元测试，覆盖 pauseSession / resumeSession 的全部分支。

目标文件：
app/src/test/java/interview/guide/modules/voiceinterview/service/VoiceInterviewServicePauseTest.java

验收标准（对着这三条交作业）

  1. 6 个用例全部通过，没有任何 @Disabled
  2. 全量测试的通过数从 16 上升，跳过数从 44 下降
  3. 你能不看书，口头讲出「为什么旧测试会 NPE」——这是本课真正要学的东西

2证据：你的测试套件 73% 是空转的

你上午跑的那次确实是绿的，这点没错。但绿的数字长这样：

测试类测试数跳过注释写的原因
VoiceInterviewServiceTest（11 个 @Nested）4343构造函数新增依赖未注入 mock，NPE，留作下一步 PR
DashscopeLlmServiceTest11RolePrompt 在 e6bebe7 被移除；构造签名变更
VoiceInterviewServicePauseTest11构造签名在多次重构后不再是 4 参
VoiceInterviewPromptServiceTest11RolePrompt / getRolePrompt 在 e6bebe7 被移除
合计44 / 60剩下 16 个才是真跑的
为什么 BUILD SUCCESSFUL 会骗人

被 @Disabled 跳过的测试不产生失败，所以构建照样成功。你看到的绿色，是「没有失败」，不是「验证过了」。 这两件事在面试里经常被混为一谈——能主动指出这个区别，本身就是个不错的信号。

3为什么这一刀比 end_phase 好

维度end_phase 不一致测试恢复（本课）
体量1–3 小时，但改动可能只有几行1–2 小时，产出 6 个用例
故事线发现 → 判断 → 改，偏单薄发现 → 定位 → 判断 → 方案 → 验证，五环齐全
可量化难量化「通过数从 16 提到 22」——面试里最硬的那种话
展示的能力读代码细心单测设计 + Mockito 注入 + 技术债识别 + 范围控制
是否真贡献是作者在注释里明确写了「留作下一步独立 PR 修复」——你做的正是他邀请的事

end_phase 降级为第二刀。做完这一刀你自然会更懂这个模块，那时候再顺手处理它。

4根因：本课的技术含量全在这里

旧测试为什么 NPE？看两组事实的对比，答案就出来了。

 坏掉的旧测试正在跑的参考测试
类VoiceInterviewServiceTestVoiceInterviewSummaryPersistenceTest
构造方式@InjectMocks手动 new VoiceInterviewService(...)
声明的 mock 数4 个7 个（全给）
服务的构造参数数7 个
结果3 个参数无人提供全部满足

VoiceInterviewService 用 @RequiredArgsConstructor，7 个 final 依赖全部走构造函数注入：

sessionRepository · messageRepository · evaluationRepository
redissonClient · properties · voiceEvaluateStreamProducer · llmProviderRegistry
最关键的一句（背下来）

@InjectMocks 解析不出构造参数时，静默传 null，不会编译报错、不会启动报错——要等到被测方法真的用到那个依赖，才在运行时炸成 NPE。
手动 new 把这个问题从运行时挪到了编译期。参数少了，编译不过。

顺便，这里还有一处发现值得你记下来：旧测试的 @Disabled 注释里只说了缺 LlmProviderRegistry，实际缺 3 个依赖。注释也是过时的。这种「文档与事实不一致」的小观察，在面试里比技术细节更能证明你真读过代码。

5工作模板：照抄这份骨架

风格不是我自己编的，是从正在跑的那个测试类提取的，同时符合 AGENTS.md 的要求：JUnit 5 + Mockito + AssertJ、中文 @DisplayName、2 空格缩进。

package interview.guide.modules.voiceinterview.service;

import interview.guide.common.ai.LlmProviderRegistry;
import interview.guide.common.exception.BusinessException;
import interview.guide.modules.voiceinterview.config.VoiceInterviewProperties;
import interview.guide.modules.voiceinterview.listener.VoiceEvaluateStreamProducer;
import interview.guide.modules.voiceinterview.model.VoiceInterviewSessionEntity;
import interview.guide.modules.voiceinterview.model.VoiceInterviewSessionStatus;
import interview.guide.modules.voiceinterview.repository.VoiceInterviewEvaluationRepository;
import interview.guide.modules.voiceinterview.repository.VoiceInterviewMessageRepository;
import interview.guide.modules.voiceinterview.repository.VoiceInterviewSessionRepository;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;
import org.redisson.api.RBucket;
import org.redisson.api.RedissonClient;

import java.util.Optional;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.ArgumentMatchers.anyString;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
@DisplayName("VoiceInterviewService 暂停/恢复")
class VoiceInterviewServicePauseTest {

  @Mock private VoiceInterviewSessionRepository sessionRepository;
  @Mock private VoiceInterviewMessageRepository messageRepository;
  @Mock private VoiceInterviewEvaluationRepository evaluationRepository;
  @Mock private RedissonClient redissonClient;
  @Mock private VoiceInterviewProperties properties;
  @Mock private VoiceEvaluateStreamProducer evaluateStreamProducer;
  @Mock private LlmProviderRegistry llmProviderRegistry;
  @Mock private RBucket<VoiceInterviewSessionEntity> bucket;

  private VoiceInterviewService service;

  @BeforeEach
  void setUp() {
    // 手动构造：参数不齐会编译失败，不会像 @InjectMocks 那样静默传 null
    service = new VoiceInterviewService(
        sessionRepository,
        messageRepository,
        evaluationRepository,
        redissonClient,
        properties,
        evaluateStreamProducer,
        llmProviderRegistry
    );
  }

  @Test
  @DisplayName("暂停进行中的会话：状态转 PAUSED、写入暂停时间、失效缓存")
  void pauseInProgressSession() {
    VoiceInterviewSessionEntity session = VoiceInterviewSessionEntity.builder()
        .id(42L)
        .status(VoiceInterviewSessionStatus.IN_PROGRESS)
        .build();
    when(sessionRepository.findById(42L)).thenReturn(Optional.of(session));
    when(redissonClient.<VoiceInterviewSessionEntity>getBucket(anyString())).thenReturn(bucket);

    service.pauseSession("42", "用户超时");

    assertThat(session.getStatus()).isEqualTo(VoiceInterviewSessionStatus.PAUSED);
    assertThat(session.getPausedAt()).isNotNull();
    verify(sessionRepository).save(session);
    verify(bucket).delete();
  }

  // 剩下 5 个用例按第 6 节的清单自己写
}

第一个用例我写完整了，剩下的留给你——照抄这个形状就行，只是前置条件、断言和 stub 不同。写测试这件事本身就是重复劳动，跑通第一个之后第二个会快很多。

6六个用例清单

被测的两个方法分支完全对称，所以用例也是对称的。这是你的测试设计，也是面试里要讲的「我怎么想覆盖面」。

#用例前置期望
1暂停进行中的会话status=IN_PROGRESS，findById 命中status→PAUSED；pausedAt 非空；verify save；verify bucket.delete()
2暂停不存在的会话findById 返回 Optional.empty()抛 BusinessException，错误码 NOT_FOUND
3暂停非进行中的会话status=PAUSED抛 BusinessException，错误码 BAD_REQUEST
4恢复已暂停的会话status=PAUSED，且设了 currentPhasestatus→IN_PROGRESS；resumedAt 非空；verify save；verify bucket.set(...)
5恢复不存在的会话findById 返回 Optional.empty()抛 BusinessException，错误码 NOT_FOUND
6恢复非暂停状态的会话status=IN_PROGRESS抛 BusinessException，错误码 BAD_REQUEST

异常断言用 AssertJ 的 assertThatThrownBy(...).isInstanceOf(BusinessException.class)。状态枚举只有四个值：IN_PROGRESS / PAUSED / COMPLETED / FAILED。

7三个一定会咬你的坑

坑一：Mockito 的严格模式会拒绝「多余的 stub」

MockitoExtension 默认 STRICT_STUBS：你 stub 了但该用例没用到，测试直接失败（UnnecessaryStubbingException）。

坏掉的旧测试是这么绕过去的：类上加 @MockitoSettings(strictness = LENIENT)，还在 setUp 里用 lenient().when(...) 全局 stub 了 Redis。

✕ 别学旧测试

把严格模式关掉，让报错消失。

问题：你同时关掉了 Mockito 最有价值的一条保护——它本来能帮你抓出无用的 stub，也就是「你以为这段代码在用，其实没走到」。

✓ 正确做法

不在 setUp 里全局 stub；每个用例只 stub 自己那条路径用到的依赖。

比如用例 2、3、5、6 会在走到缓存逻辑之前就抛异常，所以这几个用例不要 stub getBucket。严格模式这时反过来帮你验证「这条路径真的没碰缓存」。

坑二：currentPhase 没设值会 NPE

用例 4 必须给实体设 currentPhase。原因：resumeSession 最后会调 buildSessionResponse(session)，里面有一行 session.getCurrentPhase().name()；而实体中 currentPhase 没有 @Builder.Default，不设就是 null，直接 NPE。

取值：VoiceInterviewSessionEntity.InterviewPhase.INTRO（枚举是实体里的嵌套类，四个阶段 INTRO / TECH / PROJECT / HR，外加 COMPLETED）。

这个坑本身是收获

写测试时撞到的 NPE，往往就是生产代码的脆弱点。这里它说明 buildSessionResponse 隐含假设 currentPhase 非空，但没有校验。 面试里可以主动说：「我补测试时发现这个隐式契约，加了断言把它固定下来。」——比单纯「我写了 6 个测试」高一个层次。

坑三：三个依赖必须传，但整条路径用不到

evaluationRepository、evaluateStreamProducer、llmProviderRegistry 在 pause / resume 路径上一次都没被调用，但构造函数强制要求。

这是可以主动讲出来的重构观察：一个 Service 的依赖面越宽，说明它承担的职责越多。pause / resume 这种纯状态流转的逻辑，按理不该知道 LLM 和评估的存在。面试官若问「你会怎么改」，答案就是按职责拆分，或者把状态流转抽到独立的 SessionStateService。

8执行步骤

  1. 打开 VoiceInterviewServicePauseTest.java，把它整个替换成第 5 节的骨架 + 第 1 个用例（别急着一口气写完 6 个）。
  2. 跑：
    ./gradlew :app:test --no-daemon --tests "*VoiceInterviewServicePauseTest*"
    注意：类上还有 @Disabled，不删的话一个都不会跑。先删掉。
  3. 第 1 个用例绿了，再按清单逐个加。每加一个跑一次——一次加 5 个然后一起 debug 是初学者最容易浪费两小时的方式。
  4. 6 个全绿后跑全量，看通过数和跳过数的变化：
    ./gradlew :app:test --no-daemon
  5. 写下你的量化结果（通过数 16 → ?，跳过数 44 → ?）。这就是你的弹药。

想自己数通过数，用这个

python3 -c "
import glob, xml.etree.ElementTree as ET
t=s=f=0
for p in glob.glob('app/build/test-results/test/*.xml'):
    r = ET.parse(p).getroot()
    t += int(r.get('tests',0)); s += int(r.get('skipped',0))

9你的面试故事线（五环填空）

改完之后，把这段说顺。面试官要的不是「我修了测试」，是这五环之间的因果推理。

逐字稿骨架 · 做完任务后填实

发现问题：「我在跑这个项目的测试套件时注意到，60 个测试里有 44 个是跳过的——覆盖率虚高。而且构建照样是绿的，因为 @Disabled 不产生失败，所以这件事很容易被一直忽略。」

定位：「我追进去看注释，原因是语音面试模块经历了几次重构，改了服务构造函数的签名和依赖注入，但测试的 mock 没跟着改，于是这些类被直接 @Disabled 掉而不是修。」

判断：「具体到 VoiceInterviewServiceTest，它用的是 @InjectMocks，但只声明了 4 个 mock，而服务的构造函数要 7 个参数。Mockito 对解析不出的参数静默传 null，所以不报错，运行时才 NPE。有意思的是注释里只提到缺一个依赖，实际缺三个。」

方案：「我改成手动 new，让编译器替我检查参数完整性；然后不用 LENIENT，按每条路径精确 stub——严格模式反过来帮我确认某些分支确实没碰缓存。我先把 pauseSession / resumeSession 这一类做完，6 个用例覆盖状态流转的两个方向加四个异常分支。」

验证：「通过数从 16 提到 〔N〕，跳过从 44 降到 〔M〕。剩下最大的一类是 43 个 @Nested，需要 mock 出 LLM 客户端的链式调用，我评估后觉得应该单独一个 PR，避免和别的改动耦合。」

最后那句「我评估后觉得应该单独一个 PR」不要省。它展示的是范围控制——知道该在哪儿停下，是资深和初级最明显的分界线之一。很多候选人会硬做完然后做砸。
